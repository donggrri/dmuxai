# dmuxai 비전 — 개인용 에이전트 관제탑

## 목표

여러 코딩 에이전트를 **한곳에 모으고, 맥락과 실행 이력을 이어 주는 Rust 기반 코디네이터**를 만든다. Claude Code, Codex, Cursor CLI, Gemini/Antigravity, opencode, Grok 같은 기존 CLI를 새 하네스로 대체하지 않고 그대로 헤드리스로 사용한다. CLI·대시보드에서 직접 작업을 맡기거나, 다른 에이전트가 MCP로 위임할 수 있다.

목표는 지원 목록을 자랑하는 것이 아니라 개발자가 매일 자기 개발에 쓰는 도구다. Hermes Agent 같은 코디네이터의 메모리 관리 관점을 참고하되, dmuxai는 실행과 인수인계에 집중한다. 무인 실행과 사람이 진행을 보고 개입하는 **human-on-the-loop 개인 관제탑**을 함께 지향한다.

## 핵심 원칙 — 상위 에이전트가 자유롭게 제어

Grok Bot·Hermes Agent 같은 상위 에이전트는 사람이 대시보드에서 하는 일을 안정적인 **MCP와 JSON 출력 headless CLI**로 동등하게 수행할 수 있어야 한다. 작업 시작, 진행·이벤트 관찰, 실행·문제 목록, 중지·kill, delta 유지 인계, 단계 승인, 실행 요약과 Markdown 이슈 초안 조회까지 같은 제어 능력을 제공한다. 화면 자동화나 사람이 터미널 앞에 있는 것을 전제로 하지 않는다.

인터페이스는 비대화형이고 가능한 작업은 멱등적이어야 한다. 명확한 상태·오류 코드, 실행 식별자, 이벤트 스트림 또는 순번 기반 polling을 제공한다. 대시보드·MCP·CLI는 같은 소유권·권한·승인 규칙을 공유한다. “자유로운 제어”는 무제한 권한이 아니다. 출력에 비밀을 노출하지 않으며 민감 작업은 기존 승인 정책을 지킨다. `--allow-sensitive`나 `--trust-workspace-config`로 우회하지 않는다.

**현재 상태 (2026-11-08 KST, main `a28799d` 코드 확인):** MCP는 `todo_add`, `todo_list`, `run`, `status`, `events_since` 5개다. `run`은 결과까지 기다리며 `approve_plan`·`approve_plan_id` 인자를 갖는다. CLI는 `run --json`(선택적 `--progress`), `todo add/list/run`의 JSON 출력, `status --json`, `events --since … --follow --json`을 제공한다. 계획 hash를 지정하는 `run --graph --approve-plan-id …`도 있다. 이는 실행 중 임의 단계 제어 API와 같지 않다. 근거: `src/mcp_server.rs`, `src/cli.rs`.

아직 전용 실행·문제 목록/상세·종료 요약·Markdown 초안, 실행 ID 기반 중지·kill 및 delta 인계, 일반 단계 승인 인터페이스가 부족하다. MCP `run`의 결과 대기를 분리하는 비동기 시작·조회 계약과 멱등성·상태/오류·권한의 표면 간 parity 검증도 로드맵이다. 이 문서는 목표를 확정할 뿐이며 **새 MCP 구현은 기존 보류 지침대로 별도 승인 전 착수하지 않는다.**

## 왜 dmuxai인가

터미널을 여러 개 띄우는 것만으로 충분한 작업도 많다. 에이전트 하나와 대화하며 수정하는 작업이라면 네이티브 CLI가 더 단순하고 편하다. dmuxai는 그 경험을 대체하려 하지 않는다.

차이는 작업이 여러 에이전트와 실행을 거칠 때 생긴다. 사람이 실패 원인과 변경 상태를 복사하고, 다음 에이전트를 고르고, 테스트 결과를 확인하는 일을 반복하지 않도록 한다. 평소에는 MCP·백그라운드로 실행하고, 대시보드에서 진행을 관찰하며 필요할 때 중지·인계·승인한다.

이 추상화에도 비용이 있다. CLI 버전·출력 형식 변경, 관찰 공백, 불안정한 테스트 때문에 오히려 번거로울 수 있다. 테스트 연결 수가 많다고 품질이 자동 보장되는 것도 아니다. 매일의 실행 기록과 재현 가능한 검증으로 실제 효용을 증명해야 한다.

## 차별점

- **맥락은 작업에, 세션은 각 CLI에:** 작업 단위 공유 transcript와 에이전트별 `resume id`를 유지하고, 각 에이전트가 아직 못 본 delta만 전달한다. 네이티브 세션·캐시를 최대한 활용하되 실제 캐시 효과는 CLI 구현에 달려 있다.
- **벤더를 넘는 읽기 전용 리뷰:** 구현자와 다른 에이전트가 변경과 맥락을 검토한다. 모델의 의견은 보조 증거이며 테스트를 대신하지 않는다.
- **결정론적 스펙→테스트 래칫:** `spec → plan → test → wrapup` 흐름과 테스트 연결의 후퇴를 막는 기계적 게이트를 기반으로 한다. 무료·저가 모델을 기본 워커로 쓰고 실패 시에만 허용된 대안으로 올린다. 유료 사용은 별도 사용자 정책을 따른다.
- **벤더 중립적인 조합:** 서로 다른 회사의 CLI, 구독, 무료 쿼터를 함께 활용한다. 단일 벤더가 자기 제품 안에서 제공하리라 기대하기 어려운 조합을 사용자가 직접 통제한다.

## 대시보드 범위

웹 대시보드는 **유지한다**. 예외 처리뿐 아니라 평소 진행 감시와 직접 제어도 핵심 사용 방식이다.

| 범위 | 내용 / 우선순위 |
|---|---|
| 감시 | 프로세스 상태, 게이트 상태, 스트림 로그, 실행 목록·상세, 감지된 문제 |
| 우선 제어 | 소유 실행의 중지·강제 종료, delta를 유지한 에이전트 인계, 단계 승인 |
| 후순위 | 수동 재시도. 정책상 재시도 가능한 실패는 자동 1회 재시도 후 fallback 우선 |
| 미결정 | 채팅형 후속 지시 입력창은 제어 기능 검토 시 다시 결정 |

중지는 소유 run·프로세스 그룹과 권한을 검증한다. 무응답·시간 초과로 종료할 때 에이전트가 띄운 테스트·컴파일러도 같은 프로세스 그룹 단위로 정리한다. heartbeat 공백만으로 멈춤을 단정해 죽이지 않는다.

## 메모리 원칙

**dmuxai는 도메인 지식이 아니라 실행 메타데이터를 기억한다.**

1. **작업 인수인계 기억:** 변경 파일, 실패한 TC, 마지막 오류 요약, 게이트 상태와 실행 식별자를 다음 워커·리뷰어에게 전달한다.
2. **라우팅 기억:** 에이전트·모델별 성공률, 멈춤·실패 이력을 집계해 선택과 fallback에 활용한다. 관찰하지 못한 원인은 `unknown`으로 남긴다.
3. **장기 지식의 원본은 저장소:** 코딩 규칙·구조·요구사항은 `AGENTS.md`, 스펙, 래칫 예외 목록에 둔다. CLI 자체 메모리와 경쟁하는 별도 지식 저장소를 만들지 않는다.

원시 로그는 메모리의 재료일 뿐이다. 실행 종료 시 에이전트·버전·소요 시간·종료 사유·관찰된 실패 TC·변경 상태를 구조화해 요약한다. 거대한 로그 전체를 다음 프롬프트에 넣지 않는다.

실행 로그는 **로컬 전용, 90일 / 1 GiB 한도, 상세 진단 항상 기록, 저장 전 비밀 마스킹**을 기본으로 한다. 보존 한도 아래에서 상세 증거도 크기를 제한하며 누락·잘림을 표시한다. 이슈 초안은 Markdown 파일만 생성하고 자동 제출하지 않는다. 환경 스냅샷에는 dmuxai 버전·빌드 커밋, 에이전트 CLI 정확한 버전, 작업 폴더 HEAD와 변경 통계를 담되 인증 파일·환경변수·코드 본문은 수집하지 않는다. 공유 전 사람이 다시 확인한다.

## 하지 않을 것

- 코드 편집기, 전체 diff 뷰어, 파일 트리를 갖춘 웹 IDE 만들기.
- 기존 CLI 하네스·메모리·구독 체계를 재구현하거나 도메인 지식을 중복 관리하기.
- 모델의 자기 평가만 믿고 스펙·테스트 게이트를 생략하기.
- 로그·이슈 초안을 자동 업로드하거나, 사용자 승인 없이 이슈를 제출하기.
- 이 비전 문서를 근거로 TUI 제거, MCP 확장, 유료 모델 사용을 바로 실행하기. 각각 별도 범위·승인이 필요하다.

## 로드맵 3단계

### 1. 관제와 실행 증거 — 진행 중

실행 ID와 로컬 실행 로그·조회, 상세 진단·보존·마스킹, 종료 요약을 만든다. 멈춤·시간 초과 감지와 프로세스 그룹 정리를 검증한다. 대시보드 실행 화면·문제 표시 및 중지·인계·승인 동선을 연결하고, 환경 스냅샷을 포함한 Markdown 이슈 초안을 만든다. 관련 문제: [#273](https://github.com/donggrri/dmuxai/issues/273), [#253](https://github.com/donggrri/dmuxai/issues/253).

1단계 제어는 대시보드만의 기능으로 끝내지 않고 CLI/JSON·MCP parity를 완료 조건으로 삼는다. 실행·문제·요약·초안 조회, 중지·인계·승인과 비동기 진행 관찰을 공통 계약으로 설계한다. 단, MCP 구현 착수는 보류 해제 승인 후다.

### 2. 실패 인수인계 메모리

실패 요약·변경 상태·미통과 TC를 구조화하고 fallback 에이전트와 읽기 전용 리뷰어에게 주입한다. 기존 세션과 delta 전달을 유지하며 출처·미관찰 상태를 보존한다.

인수인계 요약과 delta 전달 결과도 상위 에이전트가 MCP·CLI로 확인·제어할 수 있어야 한다.

### 3. 라우팅 메모리

누적 기록에서 에이전트·모델별 성공률과 멈춤·실패 빈도를 대시보드에 표시한다. 충분한 관측과 명시적인 정책에 따라 불안정한 모델을 건너뛰거나 조기 fallback한다. 선택 이유는 사용자가 확인할 수 있어야 한다.

통계와 라우팅 근거·정책 제어 역시 대시보드와 MCP·CLI에서 동등하게 제공한다.

각 단계는 별도 스펙·테스트·작은 PR로 검증한다. 이 문서는 방향이며 모든 기능이 이미 구현됐다는 뜻은 아니다. 외부 검토 의견을 참고했으며, 충돌하는 부분은 사용자의 결정이 우선한다.
